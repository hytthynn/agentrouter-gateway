## 1. Введение

### 1.1. Назначение

**AgentRouter Gateway** — локальное приложение, предоставляющее:

- единый **OpenAI-совместимый шлюз** (`http://127.0.0.1:<port>/v1`), который можно подключить в любую IDE
  (Cline, Roo Code, Kilo Code, Cursor, Codex и др.) как обычный OpenAI-провайдер;
- **пул аккаунтов agentrouter.org** с автоматическим управлением: добавление по GitHub-креденшалам,
  автоматический выпуск безлимитных ключей, отображение баланса, ежедневный чек-ин;
- **веб-панель** в современном тёмно-лаймовом стиле: аккаунты, ключи, каталог моделей, логи, настройки.

### 1.2. Цели проекта (MVP)

| # | Цель |
|---|------|
| G1 | Добавление аккаунта AgentRouter по **логину, паролю и TOTP-секрету GitHub** + **system access token** AgentRouter, с полной автоматизацией GitHub OAuth-входа (headless-браузер) |
| G2 | При добавлении аккаунта автоматически выпускается **ключ провайдера: безлимитный, бессрочный, со всеми моделями** |
| G3 | Отображение **баланса** каждого аккаунта (в $ и quota) с автообновлением |
| G4 | **Чек-ин** вручную и по расписанию ($25/день), со всеми необходимыми обходными манёврами |
| G5 | Синхронизация и управление **каталогом моделей** провайдера |
| G6 | **Ключи шлюза** (выдаёт сам шлюз): лимит токенов или безлимит, включение/выключение, срок действия, ограничение по моделям |
| G7 | Полноценный **OpenAI-compatible шлюз** со стримингом (SSE), маршрутизацией между аккаунтами и failover |
| G8 | **Логи** запросов (per-request accounting) и системных событий |
| G9 | Тёмно-лаймовый UI, русский язык, минимум лишнего функционала |
| G10 | Готовность к продакшену **в локальном контуре**: надёжность, шифрование секретов, обработка ошибок, логирование |

### 1.3. Принципы

- **Чистая архитектура**: слой провайдера изолирован за адаптером; домен не знает про FastAPI; всё зависит от абстракций.
- **MVP без лишнего**: никакой мультиарендности, регистрации, телеметрии, облачных фич.
- **Runtime-discovery**: точные форматы ответов новых эндпоинтов валидируются в рантайме через адаптер с фолбэками (см. §2.6, §16).
- **Безопасность по умолчанию**: сервер слушает только `127.0.0.1`; все секреты шифруются AES-256-GCM.

### 2.2. Management API (консольные эндпоинты)

Аутентификация — два заголовка:

```
Authorization: Bearer <system access token>   # «Системный токен доступа» из настроек консоли
New-Api-User: <user_id>                        # числовой id пользователя (5-значный обычно)
```

| Эндпоинт | Метод | Назначение |
|---|---|---|
| `/api/user/self` | GET | Профиль и **баланс**: `data.quota`, `data.used_quota`, `data.request_count`, `data.group`, `data.username`, `data.id` |
| `/api/models` | GET | Доступные модели аккаунта (список id). Фолбэк: `/api/user/models` |
| `/api/token/?p=0&size=…` | GET | Список ключей (с полями `key`, `unlimited_quota`, `remain_quota`, `expired_time`, `status`, `used_quota`) |
| `/api/token/` | POST | **Создание ключа** — возвращает созданный объект с полным `key` (`sk-...`) |
| `/api/token/` | PUT | Обновление ключа (полный объект!) |
| `/api/token/{id}` | DELETE | Удаление ключа |
| `/api/user/checkin` | POST | **Чек-ин** (кандидат; фолбэки: `/api/user/check_in`, `/api/user/sign_in`) |

Тело `POST /api/token/` (проверенные поля):

```json
{
  "name": "agw-auto-unlimited",
  "unlimited_quota": true,       // true = безлимит (remain_quota игнорируется)
  "remain_quota": 50000000,      // иначе лимит расхода (500000 = $1)
  "expired_time": -1,            // -1 = бессрочно (unix-сек, иначе дата)
  "model_limits_enabled": false, // false = все модели
  "model_limits": "",            // или CSV/JSON список id моделей
  "group": "default"
}
```

### 2.3. Чек-ин

- Награда: **$25/день** (= 12 500 000 quota).
- Заголовки запроса: `Authorization: Bearer`, `New-Api-User`, `Content-Type: application/json`,
  `X-Requested-With: XMLHttpRequest` (как в референс-реализациях чек-ина для new-api сайтов).
- **Ключевой нюанс из FAQ провайдера:** «需要退出后重新登陆才会到账» — *бонус чек-ина зачисляется только после
  выхода и повторного входа*. Следовательно, после успешного POST-чек-ина приложение должно выполнить
  **re-login аккаунта** (GitHub OAuth через сохранённые креды, см. §9) и заново прочитать `/api/user/self`.
  Если баланс не изменился — записать warning в системный лог и повторить попытку в следующий запуск джобы.
- Статус «уже чекинились сегодня» распознаётся по `success=false` + тексту (runtime-discovery, см. §2.6).

### 2.4. Поддерживаемые клиенты (для имперсонации)

Из официального FAQ (важно для обхода WAF — §10):

> claude-code⭐, codex⭐, openclaw, pi, opencode, ohmyopencode, kilo-code, roocode, cline, crush, droid,
> qwencode, hermes, **zcode**, qoder, kimi code, craft-agent, trae, github-copilot, workbuddy, cursor,

Точные `User-Agent` и клиентские заголовки калибруются в рантайме (модуль диагностики, §8.6).

### 2.5. Известные ошибки апстрима

| Ошибка | HTTP | Причина | Действие шлюза |
|---|---|---|---|
| `Budget pool quota has been exhausted` | 402 | Дневной пул модели исчерпан | failover на другой аккаунт/модель; типизированная ошибка с подсказкой времени ближайшего пополнения (02:00/11:00 UTC) |
| `Unauthorized client detected` | 401 | WAF не распознал клиент | смена client-профиля/транспорта, failover |
| `no available channel` | 503 | нет свободных каналов у модели | retry/failover |
| `sensitive words detected` | 400 | анти-абьюз фильтр | проксировать как есть (ошибка пользователя) |
| `Invalid token.` | 401 | ключ отозван/удалён | пометить аккаунт `needs_relogin`, failover |

### 2.6. Политика runtime-discovery

Форматы ответов могут отличаться от задокументированных (форк ≠ эталонный new-api). Правила:

1. Все вызовы консольного API идут через **адаптер** `providers/agentrouter/` — никаких прямых HTTP из домена.
2. Ответ валидируется «мягко»: обязательное поле — `success`; остальное читается опционально.
3. Для чек-ина: список эндпоинтов-кандидатов перебирается по порядку, найденный кэшируется в настройках.
4. Модуль **diagnostics** (§8.6) позволяет в UI проверить любой эндпоинт и увидеть сырой ответ — для быстрой калибровки при изменении форка.

## 3. Архитектура

### 3.1. Компонентная диаграмма

```
┌────────────────────────── Локальная машина (Windows) ──────────────────────────┐
│                                                                                │
│  IDE (Cline/Cursor/Codex/...)                                                  │
│    │  base_url = http://127.0.0.1:8787/v1                                      │
│    │  api_key  = <ключ шлюза>                                                  │
│    ▼                                                                            │
│  ┌──────────────────── FastAPI (uvicorn, порт 8787) ──────────────────────┐    │
│  │                                                                        │    │
│  │  [Gateway /v1/*]──► auth key ──► Router ──► Transport(curl_cffi) ─────┼──► agentrouter.org/v1
│  │        │                       │  (round-robin,      │  (TLS-имперсонация,
│  │        ▼                       │   failover)         │   client-профили)  │
│  │  [Accounting/Logs]      [Accounts Pool]              │                    │
│  │                                                                        │    │
│  │  [REST API /api/*] ◄── Web UI (React, статика)                        │    │
│  │        │                                                               │    │
│  │  [Domain services: accounts, keys, catalog, checkin, balance, logs]   │    │
│  │        │                                                               │    │
│  │  [Scheduler: checkin, balance, session-monitor, sync, retention]      │    │
│  │        │                                                               │    │
│  │  [Automation: Camoufox headless ──► github.com OAuth ──► session] ────┼──► github.com
│  │        │                                                               │    │
│  │  [SQLite (WAL) + AES-256-GCM encrypted secrets]                        │    │
│  └────────────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2. Слои (чистая архитектура)

```
api/          → FastAPI-роутеры: валидация входа, HTTP-коды. Ноль бизнес-логики.
gateway/      → OpenAI-совместимый прокси: парсинг запроса, роутинг, стриминг, accounting.
domain/       → сервисы и сущности: accounts, keys, catalog, routing, usage, logs, checkin.
  ↳ зависит от абстракции ProviderAdapter (протокол Python)
providers/agentrouter/ → единственная реализация адаптера: management client, transport, oauth, checkin
automation/   → headless-браузер (Camoufox/Playwright), github-login, TOTP
scheduler/    → APScheduler джобы, вызывающие domain-сервисы
db/           → SQLModel ORM + Alembic миграции
core/         → конфиг (pydantic-settings), security (AES-GCM), логгер, ошибки
```

Правила зависимостей:
- `domain` не импортирует `fastapi`, `httpx`, `curl_cffi` — только протоколы и SQLAlchemy-сессию.
- `providers/*` и `automation/*` — единственные, кто ходит в сеть.
- `gateway` использует `domain.routing` и `providers` через интерфейсы.

### 3.3. Потоки (ключевые сценарии)

**Сценарий «Добавить аккаунт»** (FR-1): форма → `POST /api/accounts` → фоновая задача автоматизации:
OAuth-вход (§9) → `user_id` из localStorage → валидация system token (`/api/user/self`) →
**автосоздание безлимитного ключа** (`POST /api/token/` с `unlimited_quota=true, expired_time=-1`,
без лимитов моделей) → синк моделей → запись в БД → UI показывает прогресс в реальном времени (SSE-лог задачи).

**Сценарий «Запрос из IDE»** (FR-6): IDE → `POST /v1/chat/completions` (ключ шлюза) → проверка ключа
(активен, не истёк, модель разрешена, лимит токенов не исчерпан) → выбор аккаунта (стратегия +
healthy-фильтры) → upstream через curl_cffi с client-профилем → SSE-стрим клиенту → accounting
(токены, стоимость, латентность) → лог.

## 6. Функциональные требования

> Формат: **FR-N**. «Должно» = обязательное. Все операции через UI дублируются REST API (§7).

### FR-1. Аккаунты AgentRouter

- **FR-1.1.** Добавление аккаунта формой: имя (опц.), GitHub-логин, GitHub-пароль, **TOTP-секрет** (base32),
  **system access token**, base URL (опц., default из настроек).
- **FR-1.2.** После сабмита запускается задача автоматизации (§9) с live-логом прогресса в UI (SSE):
  1) OAuth-вход в GitHub (логин → пароль → TOTP → возможный device-OTP с запросом кода у пользователя, §9.5);
  2) завершение OAuth на AgentRouter, чтение `provider_user_id`;
  3) валидация system token (`GET /api/user/self`) — при несовпадении `user_id`/логина — ошибка шага;
  4) **авто-выпуск ключа** (FR-2.1);
  5) синк моделей (FR-4);
  6) сохранение аккаунта `status=active`.
- **FR-1.3.** Карточка аккаунта: имя, статус-бейдж, группа (`probation` — жёлтый бейдж-предупреждение),
  баланс ($, крупно + мелко quota), потрачено, последний чек-ин (+награда), actions:
  **Чек-ин**, **Обновить баланс**, **Перелогин**, **Диагностика**, **Удалить**.
- **FR-1.4.** Удаление аккаунта — с подтверждением (ввод имени); опционально «удалить ключи у провайдера»
  (DELETE /api/token/{id} для всех ключей аккаунта); локальные данные удаляются каскадно.
- **FR-1.5.** Статус `needs_relogin` выставляется автоматически при 401 от консольного API/просроченной сессии;
  карточка подсвечивается, кнопка «Перелогин» акцентна.
- **FR-1.6.** Статус `disabled` — аккаунт исключается из роутинга, но данные сохраняются.

### FR-2. Ключи провайдера (upstream)

- **FR-2.1.** При добавлении аккаунта **автоматически** создаётся ключ у провайдера:
  `name="agw-auto-unlimited"`, `unlimited_quota=true`, `expired_time=-1`, без лимитов моделей
  (`model_limits_enabled=false`) — то есть **безлимитный, бессрочный, со всеми моделями**.
  Полный `sk-...` сохраняется шифрованным; в UI отображается маскированным с кнопкой «Показать».
- **FR-2.2.** Ручное создание ключа: имя, чекбокс «Безлимит» (иначе лимит quota), срок (бессрочно/дата),
  модели (все/выбор из каталога). Выполняется `POST /api/token/` через адаптер.
- **FR-2.3.** Список ключей по аккаунтам: маскированный ключ, лимиты, расход `used_quota` (синк из списка
  `/api/token/`), статус. Действия: включить/выключить (PUT `status_only`), удалить (DELETE + подтверждение),
  показать полный ключ.
- **FR-2.4.** Ключи, созданные вне приложения, не «видны» до ручного импорта — **в MVP не входит**
  (отмечено в Phase 2).

### FR-3. Баланс

- **FR-3.1.** Баланс (`/api/user/self`: `quota`, `used_quota`, `group`) отображается в $ с точностью до цента
  + вторичной строкой quota. Кэш в БД, обновление по кнопке и по расписанию (§11).
- **FR-3.2.** Суммарный баланс пула — на дашборде.
- **FR-3.3.** Дельта баланса после чек-ина подсвечивается (+$25). Если после успешного POST-чек-ина
  `/api/user/self` не показал изменение — re-login (§2.3) и повторная проверка; при неудаче — warn-лог.

### FR-4. Каталог моделей

- **FR-4.1.** Синк моделей из `GET /api/models` каждого активного аккаунта → union в каталог;
  `account_models` — где доступна. Ручная кнопка «Синхронизировать» + расписание.
- **FR-4.2.** Таблица каталога: `model_id`, доступность (N аккаунтов), включён в шлюз (переключатель),
  источник добавления. Поиск по подстроке.
- **FR-4.3.** Модель недоступна ни на одном аккаунте → серый бейдж «нет активных аккаунтов».
- **FR-4.4.** `GET /v1/models` шлюза возвращает только `enabled=true` модели (OpenAI-формат).

### FR-5. Ключи шлюза

- **FR-5.1.** Создание: имя, **лимит токенов** (число или «безлимит»), срок (бессрочно/дата),
  модели (все/выбор). Ключ `agw-…` показывается полностью один раз при создании (и доступен «Показать»).
- **FR-5.2.** Учёт: `tokens_used` (prompt+completion), `request_count`, `last_used_at`.
- **FR-5.3.** Превышение лимита → запрос отклоняется ошибкой OpenAI-формата
  `insufficient_quota` (HTTP 429) до вызова апстрима; счётчик не обнуляется.
- **FR-5.4.** Включение/выключение, удаление (подтверждение), редактирование лимита/моделей/срока.
- **FR-5.5.** Готовые сниппеты подключения к IDE (модалка «Подключить IDE»): tabs — Cline/Roo/Kilo,
  Cursor, Codex CLI, «любой OpenAI-клиент» (`OPENAI_API_KEY`, `OPENAI_BASE_URL=http://127.0.0.1:8787/v1`),
  кнопка «Скопировать ключ».

### FR-6. Шлюз OpenAI-compatible

- **FR-6.1.** Эндпоинты: `POST /v1/chat/completions` (стрим и не-стрим), `GET /v1/models`,
  `GET /v1/models/{id}`. Аутентификация: `Authorization: Bearer <ключ шлюза>`.
  Совместимость: OpenAI Chat Completions schema; приём `stream=true`, `tools`, `response_format`,
  `temperature/top_p/max_tokens` и др. — прозрачный проксинг.
- **FR-6.2.** SSE-стриминг: чанки передаются клиенту по мере получения; TTFT фиксируется;
  `stream_options.include_usage` проксируется; при отсутствии usage в стриме — оценка токенов
  (~символы/4) с флагом `estimated`.
- **FR-6.3.** Маршрутизация: кандидаты = активные аккаунты с доступной моделью и балансом > 0
  (probation-аккаунты — в конец очереди). Стратегии: `round_robin` (default), `least_used` (по tokens),
  `sequential`. Состояние роутера — в памяти, стратегия в настройках.
- **FR-6.4.** Failover: до `max_attempts` (default 3) на коды 401/402/403/429/500/502/503/WAF-блок —
  следующий аккаунт; 400 — не ретраится (ошибка клиента). Трейс попыток — в `request_logs.attempts`.
- **FR-6.5.** 402 → типизированная ошибка клиенту (OpenAI-формат): code `budget_pool_exhausted`,
  message с подсказкой «пополнения в 02:00/11:00 UTC» и списком оставшихся аккаунтов/моделей.
- **FR-6.6.** Учёт расхода: после ответа `usage` записывается в `request_logs`, инкремент `gateway_keys.tokens_used`
  и `request_count`. При обрыве клиента (`client_abort`) — статус в лог, апстрим закрывается.
- **FR-6.7.** Ограничение параллелизма: семафор на аккаунт (default 4), на шлюз (default 16);
  при превышении — ожидание с таймаутом.
- **FR-6.8.** Ошибки — всегда в OpenAI-формате `{"error": {"type", "code", "message"}}` + корректный HTTP-код.

### FR-7. Логи

- **FR-7.1.** Логи запросов: таблица с фильтрами (период, статус, ключ, аккаунт, модель, поиск по ошибке),
  пагинация; колонки: время, модель, ключ, аккаунт, токены, стоимость, латентность (TTFT/total), статус.
  Детали попыток failover — раскрывающаяся строка.
- **FR-7.2.** Системные логи: категории `oauth/checkin/balance/sync/gateway/scheduler/security`,
  уровни, фильтры; детали JSON — раскрываются.
- **FR-7.3.** Ретеншн по расписанию (§11): request 30 дней, system 90 дней (настраивается).
- **FR-7.4.** Секреты (токены, ключи, пароли) в логах и ошибках **маскируются** (`sk-***`, `agw-***`).

### FR-8. Чек-ин

- **FR-8.1.** Ручной чек-ин кнопкой на карточке аккаунта и на дашборде (для всех аккаунтов).
- **FR-8.2.** Плановый чек-ин: ежедневно в `checkin_daily_at` ± jitter 0–15 мин на аккаунт;
  только для `status=active`; параллелизм 2, случайный порядок.
- **FR-8.3.** Логика: POST чек-ин (§2.3) → если успех → опционально re-login (настройка) →
  `GET /api/user/self` → запись награды/дельты в аккаунт + system_logs.
  «Уже чекинились» — не ошибка, `info`-лог.
- **FR-8.4.** История: последние чек-ины видны в карточке (последний + награда) и в системных логах.

### FR-9. Дашборд

- **FR-9.1.** Карточки: суммарный баланс пула, активные аккаунты (N/M), запросы за 24 ч, токены за 24 ч,
  ошибки за 24 ч, ближайший чек-ин (время).
- **FR-9.2.** Спарклайн: запросы/токены по часам за 24 ч (Recharts).
- **FR-9.3.** Блок «Статус аккаунтов» (компактный список с бейджами) + последние 10 записей логов.

### FR-10. Настройки

- **FR-10.1.** Страница: стратегия роутинга, чек-ин (вкл/выкл, время, re-login), периоды джоб,
  клиентский профиль по умолчанию (§10), лимиты параллелизма/таймаутов, ретеншн логов.
- **FR-10.2.** Изменения применяются без рестарта (hot-reload настроек планировщика).
- **FR-10.3.** Кнопка «Проверка здоровья»: ping апстрима, проверка транспора/профиля, состояние БД/шифрования,

## 8. Спецификация шлюза (OpenAI-compatible)

### 8.1. Аутентификация и ошибки

- `Authorization: Bearer agw-...`; отсутствие/невалидность → `401 {"error":{"type":"authentication_error"}}`;
  выключенный/истёкший ключ → `401` с осмысленным message; превышен лимит токенов → `429 insufficient_quota`.
- Неизвестная модель → `404 model_not_found` (если модель есть в каталоге, но выключена — тоже 404 + hint).

### 8.2. Проксинг запроса

1. Валидация ключа шлюза + лимитов + модели (FR-5/6).
2. Выбор аккаунта (FR-6.3). Используется активный `provider_keys` аккаунта (`auto`-ключ).
3. Формирование upstream-запроса: тело передаётся как есть (JSON), URL `{account.base_url}/v1/chat/completions`,
   `Authorization: Bearer <sk-...>`, клиентский профиль (§10): `User-Agent` + профильные заголовки.
4. Не-стрим: ответ транслируется как есть; `usage` фиксируется.
5. Стрим: `StreamingResponse` (`text/event-stream`), чанк за чанком, heartbeat-комментарии не нужны
   (чанки идут постоянно), закрытие при disconnect клиента.

### 8.3. Учёт

- `usage` из ответа/финального чанка → БД. Стрим без usage → оценка (chars/4), `estimated=true`.
- `cost_quota` из апстрима при наличии (если поле доступно) иначе расчёт недоступен — NULL.
- `first_token_ms` — время до первого SSE-чанка; `duration_ms` — полный.

### 8.4. Таймауты и устойчивость

- connect 15 s · first byte 180 s · total `upstream_timeout_s` (600).
- Ретраи только на идемпотентной фазе «до отправки тела стрима клиенту» (failover до первого байта).
- После первого байта стрима клиенту — failover невозможен: ошибка в стрим `[ERROR] chunk` + закрытие.

### 8.5. Формат `/v1/models`

```json
{"object": "list", "data": [{"id": "glm-4.6", "object": "model", "created": ..., "owned_by": "agentrouter"}]}
```

### 8.6. Диагностика подключения

`POST /api/accounts/{id}/diagnose` — последовательные проверки с результатами:
1. system token → `/api/user/self` (валидность, user_id совпадение);
2. ключ провайдера → `/v1/models` апстрима (WAF-верdict, транспорт);
3. каждый client-профиль (§10) — пробный запрос → ok / waf_block / auth_error;
4. список моделей, доступность.
Результат — карточка «Диагностика» в UI с зелёными/красными пунктами.

## 9. Автоматизация GitHub OAuth

### 9.1. Инструменты

- **Camoufox** — анти-детект Firefox (Playwright-совместимый API), `headless=True`, `humanize=True`,
  `locale="en-US"`; отпечаток зафиксирован на macOS-подобный (как в референсах — снижает риск device-OTP).
- **pyotp** — генерация TOTP-кода из base32-секрета пользователя.
- Storage-state кэш: `data/states/<account_id>/github.json` + cookies AgentRouter в `session_enc`.

### 9.2. Flow добавления/перелогина

```
1. Открыть {base_url}/login (SPA AgentRouter)
2. Клик «Sign in with GitHub» → github.com/login/oauth/authorize?client_id=Ov23lidtiR4LeVZvVRNL...
   (fallback: если клик не найден — прямой URL через /api/oauth/state)
3. GitHub:
   a. если уже залогинен (storage-state) → сразу страница authorize → кнопка «Authorize …»
   b. форма: #login_field ← логин, #password ← пароль → submit
   c. страница 2FA: #app_totp ← pyotp.TOTP(secret).now() → submit
   d. [если] device verification (код из письма) → см. §9.5
4. Редирект на {base_url}/oauth/github?code=... → SPA завершает обмен → сессия установлена
5. Прочитать из контекста: cookie `session` (AgentRouter), localStorage `user` → id, username
6. Сохранить github storage-state + cookies (шифровано), выставить provider_user_id
```

### 9.3. Надёжность

- Таймаут шагов 30 s; ретрай всего flow 2 раза; скриншот последнего состояния при ошибке →
  сохраняется в `data/states/<account_id>/last_error.png`, путь — в логе задачи.
- Признаки «GitHub отклонил аккаунт» (старые/подозрительные) — распознаются по тексту ошибки →
  типизированный код в UI.
- Для входа используется один инстанс браузера на задачу; задачи автоматизации — последовательно
  (глобальная блокировка), чтобы не триггерить анти-фрод GitHub параллельными логинами с одного IP.

### 9.4. Использование сессии

- Сессия AgentRouter хранится для: OAuth-перелогина после чек-ина (§2.3) и быстрой повторной авторизации.
- Management API работает на **system token** независимо от сессии — сессия не блокирует основные функции.

### 9.5. Device verification (риск GitHub)

GitHub при входе с «нового устройства» может запросить OTP из email. Поведение приложения:

1. Автоматизация детектит страницу верификации → задача переходит в состояние `waiting_user_code`
   (SSE-событие в UI: модалка «Введите код из письма GitHub»).
2. Пользователь вводит код → продолжение flow.
3. Если пользователь не отвечает 5 минут — задача падает с понятной ошибкой; storage-state сохраняется,
   чтобы при следующей попытке верификация не запрашивалась.

## 10. Стратегия обхода WAF

### 10.1. Транспорт

- Единственный транспорт к agentrouter.org — **curl_cffi** `requests` с `impersonate="chrome"`
  (актуальная версия отпечатка), HTTP/2, полная имитация заголовков Chrome.
- Все вызовы — через `providers/agentrouter/transport.py` (Singleton-сессия, keep-alive, retry-джиттер).

### 10.2. Client-профили

Профиль = {`user_agent`, `extra_headers`} — маскировка под поддерживаемый клиент (§2.4).

- Профили в БД (seed при первом запуске): `codex` (default), `claude-code`, `zcode`, `kilo-code`, `cline`.
  Точные UA-строки калибруются при разработке через модуль диагностики (§8.6) и правятся в настройках
  без пересборки.
- Профиль применяется к upstream-запросам шлюза; консольные (management) запросы ходят с профилем
  браузера (как SPA из браузера — проверено: работает).

### 10.3. Верификация

- На старте и в `/api/health`: `GET {base}/api/status` (публичный) — проверка достижимости.
- Диагностика (§8.6) даёт per-profile верdict; при `waf_block` — подсказка сменить профиль.
- Фиксация в README: «если WAF начал блокировать — обновить отпечаток curl_cffi/профиль».

## 11. Планировщик фоновых задач

APScheduler `AsyncIOScheduler` в процессе API. Джобы:

| Джоба | Расписание | Действие |
|---|---|---|
| `checkin` | ежедневно `checkin_daily_at` ± jitter | FR-8 (чек-ин → re-login → баланс), последовательность аккаунтов |
| `balance_refresh` | каждые `balance_refresh_min` | `/api/user/self` всех активных аккаунтов |
| `session_monitor` | каждые `session_check_min` | проверка сессий/токенов; `needs_relogin` при 401; авто-перелогин (если включён) |
| `models_sync` | каждые `models_sync_min` | union каталога (FR-4) |
| `retention` | ежедневно 04:00 | чистка логов по `log_retention_days` |

- Все джобы пишут в `system_logs` (категория `scheduler` + целевая).
- Пропуск при `disabled`/`needs_relogin`. Джоба чек-ина не запускается повторно, если прошлый
  запуск ещё активен (lock).
- Каждая джоба имеет ручной триггер через API (`POST /api/tasks/{job}/run`) — удобно для отладки.

## 13. Нефункциональные требования

### 13.1. Безопасность

- Bind **только `127.0.0.1`** (настраивается). CORS: только localhost-источники.
- `/api/*` без пароля (локальная зона доверия); **в Phase 2** — опциональный master-PIN.
- Шифрование секретов (§5.2); маскирование в логах (FR-7.4); логи HTTP — без тел (только метаданные),
  промпты/ответы **не сохраняются** (приватность, экономия места).
- Отчёт о секретах: ни один пароль/токен не попадает в git, БД в `data/` — в `.gitignore`.

### 13.2. Надёжность

- SQLite WAL + graceful shutdown (долгие upstream-запросы завершаются по отмене контекста).
- Автоматический рестарт джоб после падения процесса; идемпотентность чек-ина.
- Все внешние вызовы — таймауты + ограниченные ретраи с экспоненциальным backoff (кроме стримов).
- Продакшен-готовность: структурированные логи (файл `data/logs/app.log` + ротация), версионирование схемы
  Alembic, `--version`, `/api/health`.

### 13.3. Производительность

- Не-стрим запрос ≤ 64 KiB — без ощутимого оверхеда (< 5 ms на проксирование).
- Стрим — потоковый, буфер не накапливается; семафоры (FR-6.7) предотвращают исчерпание.
- 50 аккаунтов / 1000 запросов/час — целевые пределы MVP.

### 13.4. Совместимость

- Windows 10/11 (целевая), *nix — без препятствий (pathlib, uvicorn).
- Node ≥ 20, Python ≥ 3.12, uv, pnpm — описаны в README с командами установки/запуска.
